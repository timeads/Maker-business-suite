# Eventbrite

Selling workshop dates on the business's own Eventbrite account as well as in its shop and on our pages. Set up under Settings → Bookings → Eventbrite; the dates are linked under Bookings → Eventbrite.

## 1. What the current booking app does today

Read from the business's current single-tenant app (TuftBooking), every file that mentions Eventbrite:
`supabase/functions/eventbrite-webhook/` (`index.ts`, `parse.ts`, `parse_test.ts`, `eventbrite.ts`, `supabase.ts`), `supabase/functions/eventbrite-sync/` (`index.ts`, `eventbrite.ts`), `supabase/functions/eventbrite-admin/index.ts`, `supabase/migrations/20260807000100_eventbrite_integration.sql`, `20260807000200_eventbrite_sync_cron.sql`, `20260914000100_audit_fixes.sql`, `admin/src/pages/Eventbrite.tsx`, `admin/src/lib/api.ts`, `admin/src/pages/Roster.tsx`, `supabase/config.toml` and the functions workflow.

**It does not create, publish, update the details of, or cancel Eventbrite events.** The business makes each event (and its ticket types) on Eventbrite by hand. The app links a date to an event that already exists, and from then on only changes how many tickets that event's ticket type can sell. Its roster even says so when a linked date's time is changed: "update the event's date/time on Eventbrite too; it doesn't change automatically" (`Roster.tsx:1475-1478`).

What it does:

- **Connecting.** One private token for the whole app, `EVENTBRITE_PRIVATE_TOKEN`, a function secret pasted by hand. It uses the first organization the token can see (`GET /users/me/organizations/`). No OAuth.
- **Linking.** A screen (Eventbrite page in the admin) lists the account's live and started events, soonest first, with their ticket types (`GET /organizations/{org}/events/?status=live,started&order_by=start_asc&expand=ticket_classes`, one page only). For each upcoming date a person picks the event; the first ticket type is taken unless they pick another. Stored on the date as `eventbrite_event_id` and `eventbrite_ticket_class_id`. One event per date in practice (the order lookup takes the first date with that event).
- **What is pushed, and when.** Every five minutes (pg_cron calling `eventbrite-sync`), for every future, not-cancelled date with a ticket type: read the ticket type (`GET /events/{event}/ticket_classes/{class}/`), then
  - places left here > 0: set `quantity_total = quantity_sold + places left`, and un-hide the ticket if hidden;
  - no places left and Eventbrite has sold some: set `quantity_total = quantity_sold`, so Eventbrite shows "Sold out";
  - no places left and Eventbrite sold none: hide the ticket (`hidden = true`), because Eventbrite refuses a total of 0;
  - write only when something differs, as `POST /events/{event}/ticket_classes/{class}/` with a form-encoded body and dotted keys (`ticket_class.quantity_total=12`, `ticket_class.hidden=true`); a JSON body did not work (commit "form-encode ticket updates + hide-on-zero fallback").
    "Places left" counts every booking from every source and the shared room limit (`eventbrite_linked_sessions()`). Failures are logged and the next run tries again; nothing is recorded per date. The accepted tolerance was "Eventbrite may keep selling for up to about five minutes after the date fills".
- **What is read back.** A webhook on the organization for `order.placed,order.updated,order.refunded`, made by a "Register webhook" button (`POST /organizations/{org}/webhooks/`, form-encoded `endpoint_url`, `actions`; "already registered" is an endpoint in `GET /organizations/{org}/webhooks/` that starts with our address). For each call it fetches the order the body's `api_url` points at with `?expand=attendees`, then:
  - places = attendees not cancelled, refunded or deleted (at least 1); name from the order (or first + last, or the email); email from the order; phone from the first attendee who gave one, kept for reference only (`sms_opt_in` false);
  - a refund action, an order that is refunded, deleted or cancelled, or one whose every attendee is, gives all the order's places back (`release_seats` on each of its bookings, found by order number alone, so it works after the date was unlinked);
  - otherwise the order is booked on the linked date through `book_seats` (source `eventbrite`, once per order and date, a full date still booked and flagged oversold); an order already booked has its places set to the live attendee count (`adjust_booking_seats`), so one cancelled ticket of three gives one place back;
  - an order for an unlinked event, a deleted order (404 or 401 on reading it), or a date that can't be booked is answered 200 and dropped; anything else is answered 500 so Eventbrite sends it again.
- **Webhook security.** Eventbrite does not sign its webhooks. The app's address carries a shared secret (`?s=…`, `EVENTBRITE_WEBHOOK_SECRET`, compared timing-safe; 401 otherwise), and it only fetches an `api_url` on `www.eventbriteapi.com` / `eventbriteapi.com`.
- **Emails.** A new Eventbrite booking triggers the same notification run as a shop order: the confirmation email, then the reminders, thank-you and cancellation notice like any booking, and the owner's "new booking" alert. Email only: no texts to Eventbrite buyers.
- **Screens.** The Eventbrite page (connection, secret set, webhook registered, the date ↔ event table); the roster shows the source like any booking.

## 3. Eventbrite's API: what is from the current app, and what isn't

All calls go through `lib/eventbrite/client.ts` (plain `fetch`, one call at a time with a short gap, reads tried again on 429 / 5xx / lost connection, writes never). **From the current app's working code:** the base `https://www.eventbriteapi.com/v3`, the token as `Authorization: Bearer`, every path and query listed in section 1, the form-encoded dotted keys for ticket updates, the form fields for making a webhook, the fields read from a ticket type (`quantity_total`, `quantity_sold`, `hidden`), an event (`id`, `name.text`, `start.utc`, `ticket_classes[].id/name`), an organization (`id`, `name`), a webhook (`endpoint_url`), an order and its attendees (section 1), and the webhook body's `api_url` and `config.action`.

**Written from memory, not seen working in the current app** (each is used so that it does no harm if wrong):

- Following `pagination.has_more_items` / `pagination.continuation` on the events list (the current app reads one page). If Eventbrite answers differently, only the first page is shown.
- `config.webhook_id` in the webhook body, checked against the webhook id we got back. If Eventbrite doesn't send it, nothing is checked.
- The new webhook's `id` in the answer to making it, and `id` on each listed webhook. If missing, we keep no id and skip the check above.
- Eventbrite's error body (`error`, `error_description`), used only for the words shown on a failed date.
- Where the private token is in Eventbrite (Account settings → Developer links → API keys), in the connect form's help text.
- That Eventbrite sends a webhook again after a 5xx (the current app's comments assume so).
- That Eventbrite has no signature on webhooks. The current app's code says so and checks none; we found nothing to the contrary, so the secret address is the proof and the body is only a nudge.

## 4. What the owner does

1. Connections → Eventbrite: paste the private token.
2. Settings → Bookings → Eventbrite: press "Switch on order updates" (this site must be on its public https address), and tick the workshops sold on Eventbrite.
3. Bookings → Eventbrite: link each coming date to its event (the matching one is picked when it starts at the same minute). The old app's links are not brought across by the import.
4. Before switching the old app off: delete its webhook in Eventbrite (or stop its function), and its five-minute push, so the two don't both push and both book. Orders already booked in the old app arrive through the import with their Eventbrite order number (`eventbrite_order_id` in the bookings file), as Eventbrite bookings with a tag, so a later refund follows them and bringing the file in again never adds one twice, even one the suite booked from Eventbrite itself meanwhile. A file without the number brings them in as "Added by you", and a refund of one of those is told to the team rather than followed.

## 5. Not built

- Making, publishing, changing or cancelling Eventbrite events from here, including moving an event when a date's time changes. The current app never did this; if it is wanted, it is a new piece of work written from Eventbrite's documentation, not from working code.
- Signing in with Eventbrite (OAuth): it would need an Eventbrite app of ours with its keys in the environment. The pasted token is what the current app uses.
- Removing our webhook from Eventbrite on disconnect: a disconnected workspace's address simply stops being listened to.
- The price paid on Eventbrite (bookings carry 0, as before), and bringing the old app's links across in the import (its order numbers do come across).
- Cancelling from the confirmation email's link frees the place here (and so lets Eventbrite sell it again), but refunds nothing on Eventbrite, the same as for a shop order.
